# Проверка контекста при исправлении кода

Набор воспроизводит три исторических дефекта ContextIR. Это небольшой
эксперимент на известных организатору исправлениях, а не новый независимый
набор ошибок из разных проектов.

`cases.json` задает исходные ревизии, требования и воспроизведения.
`checks.py` содержит дополнительные проверки. Они не передаются участникам.
`checks_original.py` сохраняет исходную версию критерия для аудита серии
2026-10-20. В ней бюджетный тест ошибочно запрещал удалять необязательные
дубликаты: требовал исключение при уменьшении полного контекста на один токен.
После обнаружения ошибки все варианты проверяются одинаковым исправленным
критерием, без повторного запуска участников и без обратной связи модели.
Для каждого бюджета от 1 до размера полного контекста допустим отказ;
каждый принятый контекст обязан сохранять полную исходную запись для каждого
вопроса и укладываться в лимит. Хотя бы один бюджет должен быть принят.
Исходные и исправленные оценки публикуются раздельно.
В рабочую копию попадают исходники, открытые тесты и модуль, который нужен
этим тестам. Git и готовое исправление не передаются.

Сравниваются три представления одинаковых наблюдений:

- `history`: полный текст первичной диагностики;
- `summary`: свободная сводка, подготовленная той же моделью;
- `contextir_oacs`: наблюдения, сохраненные и прочитанные через OACS,
  затем подготовленные существующим ContextPipeline.

Это сравнение свежих сессий с переданной историей в виде текста. Оно не
воспроизводит внутреннее состояние настоящей продолжающейся сессии.
Семантический поиск OACS по долговременной памяти здесь не проверяется.
Наблюдения включают первичный просмотр кода, открытые тесты и попытку воспроизведения
дефекта. Истории длительных неудачных попыток в наборе нет.
Каждое наблюдение представлено названием действия, кодом завершения и выводом;
полная командная строка хранится локально, но в этот текст не включена.
ContextIR применяется один раз перед запуском исполнителя. Новые ответы
инструментов внутри сеанса не проходят через ContextIR. Перезапуски агента
с накоплением опыта между поколениями здесь не проверяются.

## Запуск

Нужны macOS, Python с `jsonschema`, настроенная OACS для проекта и работающий
Codex CLI с доступом к указанной в сценарии модели. Исторические Git-ревизии
должны присутствовать в локальном репозитории. Стенд не устанавливает
зависимости и не скачивает модели.

Из корня репозитория:

```bash
RUN_ROOT=$(mktemp -d /tmp/contextir-memory.XXXXXX)
python3 scripts/evaluate_code_memory.py prepare \
  --output "$RUN_ROOT/evidence" \
  --work "$RUN_ROOT/work" \
  --oacs-root "$PWD" \
  --cases "$PWD/data/benchmarks/code_memory/cases.json" \
  --hidden "$PWD/data/benchmarks/code_memory/checks.py" \
  --deny-read "$RUN_ROOT/evidence"

python3 scripts/evaluate_code_memory.py run \
  --output "$RUN_ROOT/evidence" \
  --work "$RUN_ROOT/work" \
  --oacs-root "$PWD" \
  --deny-read "$RUN_ROOT/evidence"
```

Если исполняемый файл не находится через `PATH`, передайте `--cli` с его
абсолютным путем команде `run`.

До измерений стенд проверяет, что открытые тесты исходной версии проходят,
дополнительные проверки выявляют дефект, а опубликованное исправление их
проходит. Фиксируются хеши набора, проверок и сценария. Между подготовкой и
завершением серии не меняйте сценарий или ревизию репозитория.

Внешний профиль macOS запрещает участникам читать и менять исходный
репозиторий, каталог доказательств и соседние рабочие копии.
Внутренний режим CLI `danger-full-access` используется только внутри этого
внешнего профиля, чтобы избежать повторного `sandbox_apply`.
Это ограничение доступа к материалам эксперимента, не изоляция всей машины.

## Интерпретация

В `measurement.json` каждого запуска сохраняются:

- прохождение дополнительных и открытых тестов, допустимость измененных файлов;
- полное время работы агента, включая его команды, и отдельное время подготовки;
- фактический `usage` CLI, включая кешированные входные токены;
- нагрузка и счетчики подкачки до и после запроса;
- причина остановки и признак завершения.

Для сводки нужно суммировать `usage` основного агента и подготовки.
`reasoning_output_tokens` не следует повторно прибавлять к `output_tokens`.
Кешированные токены входят в `input_tokens`; разница между ними показывает
входные токены, не отмеченные как кешированные.
Это учет токенов, не счет в денежных единицах.

Время запроса равно времени подготовки плюс времени работы агента.
Внешняя итоговая проверка не входит в него и записана отдельно.
Общая первичная диагностика и создание записей OACS выполняются до серии;
чтение записей и ContextPipeline измеряются заново для каждого запроса.

При прерывании CLI может не вернуть `usage`. Такое значение остается
неизвестным, его нельзя заменять нулем или оценкой по длине текста.
Ошибки инфраструктуры не являются ошибками модели.

Два повтора на трех задачах недостаточны для доказательства эквивалентности
качества или устойчивого ускорения. Порядок вариантов сбалансирован, но
удаленная очередь и состояние кеша провайдера не контролируются.
Фоновая нагрузка фиксируется без расчетной нормализации времени.

Сырые журналы оставляйте в локальном каталоге доказательств. Перед публикацией
проверяйте пути и идентификаторы. После сохранения нужных результатов удалите
только временные рабочие копии этого запуска; постоянную базу OACS не удаляйте.
